# git-extract 适用范围分析（2026-10-14）

## 背景

会话中对比了 git-extract 与 `git cherry-pick` 的机制差异（净变化 vs 历史重放、提交元数据、原子性、路径裁剪），引出问题：这个技能的可用范围是不是很小？本文是对该问题的分析记录，供后续定位调整参考。

前置结论（对比部分）：cherry-pick 是逐提交重放历史并保留 message / author；git-extract 是取 `BASE...FROM` 三点 diff 的净结果，压成单补丁原子应用，元数据按 git-commit 规则重新生成，路径裁剪（`--include` / `--exclude`）是一等公民。想完整重放历史时直接用 cherry-pick，技能没有优势。

## 结论

**机制层面的适用范围不小，但「免配置的智能」只在一个场景里——推断的先验假设是为发布准备调的。**分层看：机械层通用，推断层窄。

## 通用的部分（与场景无关）

- 三类分类里 A/C 类是纯 git 事实（base 是否跟踪、merge-base 两侧是否存在），任何分支对都成立；
- diff + pathspec 合成、原子 apply、委托 git-commit——纯机械层，不含场景假设；
- manual 模式就是「路径过滤的三点移植器」，且优先级矩阵保证显式 `--include` 能推翻一切启发式（包括 B 类判私有）。

不依赖推断的用途至少有：

1. 从 feature 分支只挑部分文件进 hotfix；
2. 把混杂分支按路径拆成多个独立 PR；
3. 把在错误分支上做的工作整体搬走；
4. 跨无祖先关系分支搬运选中文件。

## 真正窄的部分

1. **推断先验全是发布场景的**：gitignore 信号、`extra_excludes`、B 类「base 删了 = 私有」，都假设「工作分支上有不该发布的东西」。换场景这些启发式可能给错答案——如 backport 时 base 删文件是正当清理而非私有，B 类会误排（需显式 `--include` 推翻或用 manual）。
2. **原子全有全无 + 禁 `--3way`**：分支距离越远冲突越多，一冲突就整体停。冲突频繁的场景里 cherry-pick 的逐提交 + 3way 更实用。
3. **净变化语义**：适合「把最终状态搬过去」，不适合「重放演进过程」（v1 无 `--mode commits`，有意取舍——下游 squash 合并会抹平提交粒度）。
4. **硬边界**：无共同祖先的 orphan 分支直接在 merge-base 处失败；只搬已提交内容。

## 技能定位

不是替代 merge / cherry-pick，而是填两者之间的空档——**「远亲分支间的、路径可裁剪的、squash 友好的单次搬运」**：

| 需求 | 归属 |
| --- | --- |
| 完整合并 | merge |
| 历史重放（保留 message / author） | cherry-pick |
| 选择性搬运 | git-extract |
